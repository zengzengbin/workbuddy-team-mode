# WorkBuddy 小队模式

本技能适用于 WorkBuddy。由当前主 Agent（会话中的你）分解任务、派发工作并最终验收；不改变主 Agent 自身的模型。四个角色通过专家团（expert team）注册，成员由你调用内置 **AgentTool**（`name` 参数传成员中文角色名）派发。

## 启用与退出

用户在消息中单独一行输入以下任一开启口令（不必是第一行，任务写在口令行之外的其他行）：

```text
$workbuddy-team-mode
```

```text
开启小队模式
```

开启口令接受 `开启`、`打开`、`启动` 三种说法，`小队模式` 前可带可不带 `WorkBuddy`（`开启 WorkBuddy 小队模式`、`打开小队模式`、`启动小队模式` 均可），对大小写和半角/全角空格不敏感（`开启workbuddy小队模式` 也可），但必须独占一行；句子中间提到口令、代码块和引用行里的口令不算。`使用 $workbuddy-team-mode` 同样算启用。

已成功启用时，该条回复必须先输出一行 `👾 已开启小队模式`，再继续处理任务。后续回复不重复输出该行。

启用后，当前聊天的后续任务都继续使用小队规则，直到用户在消息中单独一行明确输入：

```text
退出小队模式
```

退出口令接受 `退出`、`关闭` 两种说法（`关闭 WorkBuddy 小队模式` 也可，大小写与空格不敏感）。成功退出时先输出一行 `👾 已关闭小队模式`，再继续处理任务。任务完成或普通回复结束不会自动退出。

`查看小队状态`（`查询小队状态`、`查看小队模式` 等写法均可，独占一行）用于查询当前聊天是否已启用。

## 派发

1. 简单问题或主 Agent 能直接完成的短任务直接处理。只有独立子任务确有收益时才派发；一个问题默认一个成员，不凑满四个角色，独立工作才并行。
2. 用内置 **AgentTool** 派发，在 `name` 参数中传入成员的中文角色名（探索 / 执行 / 评审 / 专家顾问）。禁止派发角色表之外的成员，禁止通过 shell/CLI 另开代理绕过限制。
3. 每次派发写清：问题或交付物、必要背景、范围、验收依据、以及该角色的模型/档位意图（见下方"角色模型配置"）。执行任务必须有唯一文件/模块负责人；成员共享工作区，不得撤销他人修改。主 Agent 负责跨任务决策与整合。
4. 给探索、评审、专家顾问的任务说明要独立、精简，提供原始证据和用户约束，把怀疑当线索而非结论。所有跨成员信息流必须经你中转，不得让成员互连。
5. 小队成员不得继续派发子 Agent；需要协作时向你回报。探索/评审没有写入和 shell 工具，需要动态验证时由你直接执行或派执行角色，不得让它们声称自己运行过。
6. 专家顾问默认交付分析与建议；只有你明确交办交付物和写入范围时才执行建模、自动化或实现。
7. 派发失败、角色缺失或模型不可用时，报告具体缺口，不悄悄换角色、不降低验收标准。缺失的独立评审必须如实说明。
8. 等待派发的任务结束并核验结果后再交付。是否做评审由风险和用户需求决定，不因改动行数机械扩队。

## 角色模型配置（一次性初始化）

角色模型选型是**一次性**的，不是每次对话都问：

1. 首次启用小队模式时，读取 `references/model-menu.md`，把完整菜单（供应商、模型、思考强度、四角色推荐方案）一次性摆给用户，给出推荐，请用户选择并确认，然后按 `references/team-config.template.md` 生成 `references/team-config.md`。
2. `references/team-config.md` 生成后，之后每次启用都直接读取该文件取得各角色的模型/档位意图，**不再重复询问**。
3. 仅当 `team-config.md` 缺失或损坏时，才重新走一次选型。
4. 平台限制（必须如实，详见 model-menu.md"平台限制"一节）：WorkBuddy 不支持按成员固定模型，AgentTool 也不能指定模型。配置的定位是"意图记录 + 派发声明 + UI 档位建议"：派发时在任务说明中写明该角色的模型/档位意图；如需硬性固定，引导用户在 WorkBuddy UI 的模型与档位选择器设置。若技能安装目录不可写，配置可保存在用户工作目录，并在配置内记录实际路径，后续按该路径读取。

## 角色表

| 角色（AgentTool name） | 职责 |
|---|---|
| 探索 | 只读定位大型代码库的文件、入口、调用关系 |
| 执行 | 在明确的文件归属内实现、修改和验证 |
| 评审 | 独立只读评审稳定产物，提供有证据的问题 |
| 专家顾问 | 复杂决策、疑难诊断或明确交办的复杂任务 |

各角色的完整职责、边界和汇报要求见 [roles.md](references/roles.md)。

## 评审与收尾

评审稳定的修改及相关需求，不扩大为全库清理。要求具体位置、可复现影响和建议；无实质问题时明确说未发现。你决定采纳哪些建议，实施后按影响验证。评审后相关文件又改变时，补充检查变更部分。区分静态校验、工具运行和真实使用验收。

安装、平台机制（专家团注册、AgentTool 派发、配置与状态文件）详见 [runtime.md](references/runtime.md)。
